# AI 검증루프 v1

v1 · 2회차 (2026-10-06)

오늘 바뀐 점:
- 6절 판정 기준의 "충분한가" · "적절한가" 두 문장을 체크리스트 v1 의 예/아니오 조건으로 바꿨다.
- 교차 검증 대상을 "중요한 변경"에서 체크리스트 2절(치명) 항목에 닿는 코드를 건드리는 변경으로 정했다.
- 심각도에 "반려"를 추가하고, 경고는 승인을 막지 않으며 요청 문장을 받지 못하면 반려라고 적었다.

AI 가 만든 변경분과 외주사 PR 을 머지하기 전에 거치는 절차다. **만든 쪽과 검증하는 쪽을 분리**하고, 판정은 `templates/approval-checklist.md` 의 네 기준으로 한다.

## 1. 왜 분리하나

만든 세션은 자기 코드를 옹호한다. 같은 컨텍스트 안에서 "잘 됐는지 확인해 주세요"라고 물으면 만든 이유를 다시 설명받을 뿐이다. 검증은 **변경분만 보는 새 컨텍스트**에서 한다.

## 2. 패턴

| 패턴 | 방법 | 쓰는 때 |
|---|---|---|
| 만든 세션 → 리뷰 세션 | 새 터미널에서 Claude Code 를 새로 띄워 diff 만 보게 한다 | 기본. 모든 변경 |
| Claude 생성 → 다른 모델 리뷰 | 새 터미널에서 `claude --model sonnet` 처럼 다른 모델로 새 세션을 띄워 같은 diff 와 체크리스트를 넘긴다 | 체크리스트 2절(치명) 항목에 닿는 코드를 건드리는 변경: 비밀값 · 설정, 삭제 · 수정 쿼리, `db/`, 인증 · 권한 · CORS, SQL · JPQL 쿼리 |
| 리뷰어 Sub-agent | 읽기 전용 리뷰어를 `.claude/agents/` 에 정의해 두고 위임한다 | 같은 세션 안에서 격리된 컨텍스트로 리뷰할 때 |

## 3. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 만든 세션 | 구현, 테스트 작성, 리뷰 결과 반영 | 자기 변경의 승인 판정 |
| 리뷰 세션 | diff 읽기, 체크리스트 대조, 테스트 실행, 이슈 목록과 판정 | **코드 수정.** 고치기 시작하면 그 순간 "만든 쪽"이 된다 |
| 사람 | 요청 범위 확정, 리뷰 이슈의 수용 · 기각, 최종 머지 | 리뷰어의 판정을 읽지 않고 머지 |

## 4. 절차

1. **요청 범위 확인.** 무엇을 요청했는지 한 문장으로 받는다. 범위가 주어지지 않았으면 판정하지 말고 먼저 묻는다. 답을 받지 못하면 "요청 범위 이탈 없음"을 미충족으로 두고 반려한다.
2. **변경 파일 목록과 diff 읽기.** `git diff --stat <범위>` 로 목록을 먼저 보고, 파일마다 diff 를 읽는다. patch 파일이면 `git apply --stat` 으로 목록을 뽑는다.
3. **체크리스트 대조.** `templates/approval-checklist.md` 를 읽고 항목마다 예 · 아니오 · 확인 필요 중 하나로 표시한다. 확인 필요는 사람에게 묻고, 답을 받기 전에는 "예"로 세지 않는다.
4. **테스트 실행.** 변경된 모듈의 테스트만 실행한다. 어느 명령을 쓰는지는 팀 `CLAUDE.md` 의 빌드 · 테스트 명령을 따른다. 결과는 통과 · 실패 수와 실패한 테스트 이름만 남기고 전체 로그를 대화에 싣지 않는다.
5. **판정.** 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다. 경고 항목이 아닌 항목에 "아니오"가 하나라도 있는 기준은 미충족이고, 미충족 기준이 하나라도 있으면 반려다.
6. **되돌리기.** 리뷰 결과를 만든 세션에 넘긴다. 치명 · 반려 이슈는 모두 고친다. 경고 · 제안 이슈는 사람과 수용 · 기각을 정한 뒤 수용한 것만 고친다. 고친 뒤 다시 2번부터 돈다.

## 5. 출력 형식

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 항목 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
```

- 이슈 한 건은 심각도(치명 / 반려 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 네 항목을 모두 채운다.
- 치명 · 반려 이슈의 근거에는 체크리스트 항목 번호(예: 1-3)를 함께 적는다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 따로 적는다.

## 6. 판정 기준 (v1)

항목 문장은 `templates/approval-checklist.md` 가 기준이다. 여기에는 기준마다 반려가 되는 조건만 적는다.

| 기준 | 반려가 되는 조건 | 경고로 두는 것 |
|---|---|---|
| 테스트 통과 | 실패 · 오류 1건 이상. 테스트가 없는 새 public 메서드 1개 이상(getter · setter · 생성자 · record 자동 접근자 · `equals` · `hashCode` · `toString` 제외). 기존 테스트 삭제 · 건너뛰기 | 예외 경로 테스트 없음 |
| 치명 이슈 0건 | 목록 5종(비밀값 · 개인정보 노출, 데이터 손실, 인증 우회, SQL 문자열 조립, 운영 DB 접속) 중 1건 이상 | 목록에 없는 문제 전부. 치명으로 올리려면 사람에게 묻는다 |
| 요청 범위 이탈 없음 | 요청 문장 없음. 요청 문장으로 설명되지 않는 파일 1개 이상. 요청으로 고친 파일 안에서 import 정리가 아닌 무관한 변경 1건 이상 | 없음 |
| 컨벤션 준수 | 계층 규칙 위반(컨트롤러의 Repository 주입 · SQL 문자열, 다른 도메인 Repository 주입, 컨트롤러의 엔티티 반환, 컴포넌트 · 훅의 `fetch` 직접 호출). 빈 `catch`. `System.out` · `System.err` · `e.printStackTrace()` · `console.log` | 이름 규칙 위반, public setter 추가(사람 확인 필수), 그 밖의 팀 `CLAUDE.md` 코딩 컨벤션 위반 |

경고와 제안은 승인을 막지 않는다. 이슈 목록에 남기고 수용 · 기각은 사람이 정한다.

## 7. 하지 말 것

- 리뷰 세션은 코드를 수정하지 않는다. 보고만 한다.
- 테스트를 실행하지 않고 "통과"라고 쓰지 않는다. 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실을 적고 사람에게 기동을 요청한다.
- 요청 범위를 모르는 상태에서 "범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈 0건이 나오면 "경고 · 제안 수준까지 다시 봐 달라"고 한 번 더 요청한다. 0건은 결과일 수도, 안 본 것일 수도 있다.
