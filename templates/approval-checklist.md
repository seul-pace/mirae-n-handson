# 승인 체크리스트 v1

v1 · 2회차 (2026-10-06)

오늘 바뀐 점:
- 모든 항목을 예/아니오로 답하는 문장으로 바꿨다. "충분하다" · "심각한" · "지나치게" · "적절하게"로 쓴 항목 4개를 셀 수 있는 조건으로 교체했다.
- 치명 이슈를 닫힌 목록 5종(비밀값 · 개인정보 노출, 데이터 손실, 인증 우회, SQL 문자열 조립, 운영 DB 접속)으로 정했다.
- 범위 밖 변경은 요청으로 고친 파일 안의 import 정리만 허용하고, 컨벤션 위반을 반려 항목과 경고 항목으로 나눴다.

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 네 기준이 **모두** 충족되어야 승인이다. 하나라도 미충족이면 반려.

## 답하는 법

- 모든 항목은 "예" 또는 "아니오"로 답한다. 변경분에 해당 코드가 없는 항목은 "예"다.
- 경고 항목이 아닌 항목에 "아니오"가 하나라도 있으면 그 기준은 미충족이다.
- 예/아니오로 답할 수 없는 항목은 "확인 필요"로 적고 사람에게 묻는다. 답을 받기 전에는 "예"로 세지 않는다.

## 심각도 정의

- **치명** — 2절의 목록 5종에 해당하는 문제. 1건이라도 있으면 반려. 목록에 없는 문제는 치명으로 올리지 않는다. 올려야 한다고 보면 경고로 적고 사람에게 묻는다.
- **반려** — 1 · 3 · 4절에서 경고 항목이 아닌 항목을 "아니오"로 만든 문제. 1건이라도 있으면 반려.
- **경고** — 치명 · 반려가 아니면서 팀 `CLAUDE.md` 규칙을 어겼거나, 오동작하는 입력 · 조건을 `파일:줄번호` 로 댈 수 있는 문제. 승인을 막지 않는다. 수용 · 기각은 사람이 정한다.
- **제안** — 규칙 위반이 아니고 오동작하는 입력 · 조건도 댈 수 없는 개선 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 1-1. 변경된 모듈의 테스트 명령(팀 `CLAUDE.md` 의 빌드 · 테스트 명령)을 이 검증에서 직접 실행했다.
- [ ] 1-2. 실행 결과에 실패 · 오류가 0건이다.
- [ ] 1-3. `src/main` 에 새로 추가된 public 메서드마다 그 메서드를 직접 호출하는 테스트가 1개 이상 있다. 컨트롤러 메서드는 `@WebMvcTest` 로 그 URL 을 호출하는 테스트여야 한다.
- [ ] 1-4. 기존 public 메서드에 파라미터나 분기가 추가됐다면 추가된 파라미터 · 분기를 지나는 테스트가 1개 이상 있다.
- [ ] 1-5. `modern/web` 에 새로 `export` 된 함수 · 컴포넌트 · 훅마다 그것을 호출하거나 렌더링하는 테스트가 1개 이상 있다(타입 · 인터페이스 export 는 제외).
- [ ] 1-6. 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 없다.

1-3 에서 제외하는 메서드: getter · setter · 생성자 · record 자동 접근자 · `equals` · `hashCode` · `toString`. DTO 의 `static from` 팩토리는 제외하지 않는다.

경고 항목("아니오"여도 미충족이 아니다):

- [ ] 1-7. 새 public 메서드에 예외를 던지는 경로가 있다면 그 경로를 지나는 테스트가 1개 이상 있다.

## 2. 치명 이슈 0건

비밀값 · 개인정보 노출

- [ ] 2-1. 비밀번호 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처에 리터럴로 들어 있지 않다(실습용 더미 값 `app-pass` 는 예외).
- [ ] 2-2. 학생 식별자(`STU-…`) · 이메일 · 토큰 값을 로그에 찍는 코드가 없다.
- [ ] 2-3. 비밀번호 · 토큰 · 키를 응답 본문에 싣는 코드가 없다.
- [ ] 2-4. 학생 식별자 · 이메일을 응답 본문에 새로 싣는다면 요청 문장에 명시돼 있다.

데이터 손실

- [ ] 2-5. `DELETE` · `TRUNCATE` · `DROP` · `UPDATE` 쿼리나 리포지토리 `delete…` 호출이 새로 생겼다면 요청 문장에 그 삭제 · 수정이 명시돼 있다.
- [ ] 2-6. `db/` 의 스키마 · 마이그레이션 · 시드 데이터 변경이 있다면 요청 문장에 명시돼 있다.

인증 우회

- [ ] 2-7. 인증 · 권한 검사를 지우거나 건너뛰게 만든 코드가 없다.
- [ ] 2-8. CORS 허용 origin · 메서드를 늘렸다면 요청 문장에 명시돼 있다.

SQL 문자열 조립

- [ ] 2-9. 변수를 `+` · `String.format` · `formatted` · 텍스트 템플릿으로 이어 붙여 SQL · JPQL · 네이티브 쿼리를 만드는 곳이 없다(상수끼리 잇는 것은 해당하지 않는다).

운영 DB 접속

- [ ] 2-10. 운영 DB 호스트(`prod-db` 등)에 접속하는 설정 · 명령이 없다.

## 3. 요청 범위 이탈 없음

이탈이 1건이라도 있으면 미충족이다. 팀 `CLAUDE.md` 는 요청 범위 안 파일의 포맷팅도 허용하지만 이 체크리스트는 import 정리만 허용한다.

- [ ] 3-1. 요청 문장이 한 문장으로 확인되었다(없으면 먼저 묻는다. 답을 받지 못하면 "아니오"다).
- [ ] 3-2. 변경 파일 목록의 모든 파일이 요청 문장으로 설명된다(요청 코드를 검증하는 테스트 파일의 추가 · 수정은 범위 안이다).
- [ ] 3-3. 요청으로 고친 파일 안에서 요청과 무관한 변경은 import 정리뿐이다(포맷팅 · 메서드 추출 · 이름 변경 · 주석 수정은 이탈이다).
- [ ] 3-4. 의존성 추가 · `application.yml` 변경 · `legacy/` 수정이 있다면 요청 문장에 명시돼 있다(`db/` 변경은 2-6 에서 본다).

## 4. 컨벤션 준수

- [ ] 4-1. 팀 `CLAUDE.md` 의 코딩 컨벤션과 금지 사항을 대조했다(`convention-check` Skill 이 있으면 그 결과를 쓴다).
- [ ] 4-2. 컨트롤러에 Repository 주입이나 SQL 문자열이 없다.
- [ ] 4-3. 다른 도메인 패키지의 Repository 를 주입한 곳이 없다.
- [ ] 4-4. 컨트롤러가 엔티티를 반환하지 않고 DTO 를 반환한다.
- [ ] 4-5. `modern/web` 의 컴포넌트 · 훅에서 `fetch` 를 직접 호출하는 곳이 없다.
- [ ] 4-6. 빈 `catch` 블록이 없다.
- [ ] 4-7. `System.out` · `System.err` · `e.printStackTrace()` · `console.log` 가 없다.

경고 항목("아니오"여도 미충족이 아니다. 이슈를 경고로 적는다):

- [ ] 4-8. 클래스 · 메서드 · 필드 · 상수 이름이 팀 `CLAUDE.md` 의 이름 규칙을 따른다.
- [ ] 4-9. `src/main` 에 public setter 가 추가되지 않았다("아니오"면 사람에게 이유를 묻고 받은 답을 판정 보고에 적는다).
- [ ] 4-10. 4-2 ~ 4-9 에 없는 팀 `CLAUDE.md` 코딩 컨벤션(`record` DTO, `.toList()`, 와일드카드 import, 로그 형식 · 레벨, `@DisplayName` 등) 위반이 없다.

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 심각도는 치명 / 반려 / 경고 / 제안 중 하나로 적고, 치명 · 반려 이슈의 근거에는 항목 번호(예: 1-3)를 함께 적는다. 코드는 수정하지 않는다.
